## 1、前言

之前在学习heap相关内容的时候总好奇为什么大家都在以2.35版本的glibc举例，尤其是house of apple 2，最近在pwn.college上面学了一些题目（https://pwn.college/program-security/dynamic-allocator-misuse/），才真正理解2.35版本的“划时代”性。



## 2、2.35之前

在glibc2.35版本之前，大家的heap题都还是很固定的套路：先泄露libc地址，再用堆漏洞改fd获得任意地址写，然后把堆的链表改到"__free_hook"上面，把对应的指针改成system，把某个chunk里写入"/bin/sh"，最后释放那个堆，这样表面上的'free(chunk)'，实际就会变成'system("/bin/sh")'。这样看起来十分套路化。

"__free_hook"其实就是一个指针，在旧版本的glibc里free()函数会先检查它是否为空，如果不为空，则可以直接调用它里面写好的函数指针，所以改成system就可以直接调用了。

在2.35版本之前，glibc进行了一些大版本的变化：
2.26：引入tcache，free时优先进入tcache，malloc优先从tcache取，每个大小最多缓存7个，LIFO。

2.29：加入tcache的double-free检查：chunk进入tcache时，将key字段设为当前线程的tcache指针；free时，如果e->key == tcache，则继续遍历对应的tcache链表，确认该chunk已经存在后才报错：double free。（同时2.29版本加入unsortedbin的检查：检查victim->bk->fd是否指向victim，这样使得unsortedbin attack变得更加困难）

**2.32：加入safe-linking，保护fastbin和tcache的单向链表：存储的指针不再是一个简单的地址，而是异或编码的结果：编码后的指针=（存放当前fd指针的字段地址>>12）^下一块chunk地址，也就是要把存放该指针的字段地址先向右移12位，再把结果与原始的下一个节点指针异或；同时增加chunk地址对齐检查，在常见的x86-64环境下，要求地址必须十六字节对齐，也就是必须是0x10的整数倍。**

**2.34（最重要更新）：移出了"__free_hook"等hook机制。**

2.35：继承这些机制，新的堆利用时代。

所以并不是2.35版本突然划时代了，而是在2.35版本之前就已经加入了很多安全检查机制，它不过是一个”集大成者“，并且是Ubuntu 22.04 LTS 版本，于是成为一个经典的版本。



## 3、2.35版本中_IO_FILE 的相关介绍

到2.35版本，因为移除了hook机制，已经没办法按照旧时的思路进行`__free_hook->system`的攻击手段了，大家开始寻找新的攻击对象：”_IO_FILE“

glibc里面的”FILE“并不是一个简单的数据结构，常见的“stdin”"stdout“”stderr“等返回的文件流，底层都会使用”_IO_FILE“相关的结构体进行管理。

一个FILE对象保存的对应虚函数表，glibc在进行读、写、刷新缓存区等操作的时候，最终会通过这些函数指针执行相应的操作。所以如果可以控制FILE的一些关键字段，就能影响IO操作过程中的函数调用，这就是FSOP的基本思想。



#### 3.1、  _IO_FILE到底是什么

基于linux“一切皆文件”的思想，我们可以把一切IO设备看成“文件”，即使它可能并不是我们常说的“磁盘文件”。操作系统真正提供的其实是文件描述符fd，例如：0->stdin，1->stdout，2->stderr，3->某个特殊的文件……，这个fd代表的是一个已经打开的IO对象，于是glibc需要一个结构体来记录：

- 这个文件对应哪个fd
- 读到哪里了，写到哪里了
- 缓冲区在哪里
- 调用哪些函数处理它

而这个结构体就是 _IO_FILE。



#### 3.2、  _IO_FILE长什么样

找到了2.35版本的libc关于_IO_FILE的源码：[struct_FILE.h - libio/bits/types/struct_FILE.h - Glibc source code glibc-2.35 - Bootlin Elixir Cross Referencer](https://elixir.bootlin.com/glibc/glibc-2.35/source/libio/bits/types/struct_FILE.h)

下面对这个结构体进行简单分析（前面有一些关于结构体和宏定义和声明就略过了）：

```c
struct _IO_FILE
{
  int _flags; // 表示这个流当前的状态,如：是否到EOF,是否允许读、写,是否使用缓冲……
  //　下面这8个是很重要的内容
  char *_IO_read_ptr; // 当前读指针(下一个读的字节就在这里)
  char *_IO_read_end; // 读缓冲区有效数据末尾
  char *_IO_read_base; // 整个读缓冲区的起点
  char *_IO_write_base; // 整个写缓冲区的起点
  char *_IO_write_ptr; // 当前写指针(已经写到哪里)
  char *_IO_write_end; // 整个写缓冲区的末尾(边界)
  char *_IO_buf_base; // FILE使用的实际缓存区的起始
  char *_IO_buf_end; // FILE使用的实际缓存区的末尾
  
  //　下面三个：用于回退，不重要
  char *_IO_save_base; 
  char *_IO_backup_base;
  char *_IO_save_end;

  struct _IO_marker *_markers; // 记录流一些位置标记,不重要

  struct _IO_FILE *_chain; // 记录下一个FILE,多个FILE可以形成链表,_IO_list_all就是链表头

  int _fileno; // fd(文件描述符)
  int _flags2; // 扩展状态标志,和上面的flags类似
  __off_t _old_offset; // 文件偏移,不重要

  unsigned short _cur_column; // 记录输出所在列,不重要
  signed char _vtable_offset; // 并不是vtable,不重要
  char _shortbuf[1]; // 小缓冲空间,不重要

  _IO_lock_t *_lock; // 互斥锁
// 下面这个if就是为了兼容,新版的直接忽略if就好了
#ifdef _IO_USE_OLD_IO_FILE
};

struct _IO_FILE_complete
{
  struct _IO_FILE _file;
#endif

  __off64_t _offset; // 偏移

  struct _IO_codecvt *_codecvt; // 普通字符和宽字符之间转换:char<->wchar_t
  
  // 很重要的一个指针
  struct _IO_wide_data *_wide_data; // 用来处理宽字符wchar_t,其中保存了宽字符模式下对应读写buffer,状态,函数表等
  
  // 下面都不重要
  struct _IO_FILE *_freeres_list;
  void *_freeres_buf;
  size_t __pad5;
  int _mode;

  char _unused2[15 * sizeof (int) - 4 * sizeof (void *) - sizeof (size_t)];
};

// 读/写缓冲区还有内容就暂时不调用syscall,等缓存区用完了再调用
#define __getc_unlocked_body(_fp)					\
  (__glibc_unlikely ((_fp)->_IO_read_ptr >= (_fp)->_IO_read_end)	\
   ? __uflow (_fp) : *(unsigned char *) (_fp)->_IO_read_ptr++)

#define __putc_unlocked_body(_ch, _fp)					\
  (__glibc_unlikely ((_fp)->_IO_write_ptr >= (_fp)->_IO_write_end)	\

   : (unsigned char) (*(_fp)->_IO_write_ptr++ = (_ch)))

// EOF检测
#define _IO_EOF_SEEN 0x0010
#define __feof_unlocked_body(_fp) (((_fp)->_flags & _IO_EOF_SEEN) != 0)

#define _IO_ERR_SEEN 0x0020
#define __ferror_unlocked_body(_fp) (((_fp)->_flags & _IO_ERR_SEEN) != 0)

#define _IO_USER_LOCK 0x8000

#endif
```

#### 3.3、  其他重要的结构体

①在_IO_FILE之外，还有一层结构体：

```c
struct _IO_FILE_plus
{
  FILE file; // 这个FILE就是_IO_FILE
  const struct _IO_jump_t *vtable;
};
```

也就是说在这个_IO_FILE的下面还有一个vtable指针，它的作用是：不同文件流需要不同操作，vtable就准备了不同的函数表，最终要执行某些动作时就从vtable里找到函数。（可见附录部分）



②在这里介绍一下刚才提到的“很重要的指针”：`_wide_data`

```c
struct _IO_wide_data
{
  // 下面8行和_IO_FILE一样,都是缓冲区
  wchar_t *_IO_read_ptr;
  wchar_t *_IO_read_end;
  wchar_t *_IO_read_base;
  wchar_t *_IO_write_base;
  wchar_t *_IO_write_ptr;
  wchar_t *_IO_write_end;
  wchar_t *_IO_buf_base;
  wchar_t *_IO_buf_end;	

  // 下面三个,用于回退,不重要
  wchar_t *_IO_save_base;
  wchar_t *_IO_backup_base;
  wchar_t *_IO_save_end;

  __mbstate_t _IO_state; // 当前字符转换状态
  __mbstate_t _IO_last_state; // 之前的转换状态
  struct _IO_codecvt _codecvt; // 字符编码转换

  wchar_t _shortbuf[1]; // 小缓冲区

  const struct _IO_jump_t *_wide_vtable; // 十分重要,宽字符的vtable函数表,单独一套,功能和上面的一样
};
```



③_IO_wfile_jumps：是宽字符FILE使用的虚函数表，作用和普通FILE的 _IO_file_jumps类似（这两个就是刚才结构体里vtable指针指向的结构体）



## 4、 House Of Apple 2

基于上述思路，我们可以这样考虑：_IO_list_all里面存的是FILE链表，正常情况下他会指向一个正常的FILE结构体，但是如果我们利用之前的堆任意写，先把它里面存放的地址改了，改成一个堆地址，再往这个堆地址里写入我们伪造的FILE，这样他就会执行我们想让他执行的命令了。

整体流程：伪造FILE->伪造vtable->把函数指针改成system->触发IO

现在高版本又加入了对于vtable的检查，导致FILE->vtable的地址不能随便指向heap上的地址了，但可以写glibc里合法vtable仍然可以使用。

由于我们无法修改正常FILE的vtable到我们想要的地址，而_IO_wide_data里也有一个vtable，并且这个没有检查，如果能覆盖这个vtable，最终也能达到我们想要的目的。如果想覆盖这个vtable，就要进入“宽字符”，也就是把FILE的vtable改成 _IO_wfile_jumps的地址（它也是一个和vtable类似结构的结构体），这样接下来就会执行overflow，但由于他是“wfile”，所以执行的是 _IO_wfile_overflow() 这个函数，继续执行的话会调用 _IO_wdoallocbuf() 函数，它又会调用 _IO_WDOALLOCATE(fp) 这个函数，然后这个函数又会使用fp->_wide_data  ，从而调用这个结构体里面的  _wide_vtable，所以最终需要伪造三个内容：

_IO_FILE_plus：把他的vtable写成_IO_wfile_jumps的地址

_IO_wide_data：把他的vtable指针写成伪造的wide_vtable地址

wide_vtable：把他里面本来应该是调用的函数地址改成内容，实现其他函数的调用，如：system或orw

这样House Of Apple2就已经建立好完整的IO链了，最后调用exit或者main函数return的时候，系统会调用fflush()函数，它会触发fp->vtable->overflow，也就是触发_IO_wfile_overflow() 这个函数，于是就顺着这个链执行了system或orw，最终得到flag。
